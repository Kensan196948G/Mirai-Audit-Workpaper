# 運用・保守・障害対応計画

## 1. 運用目的

監査の独立性を損なわず、安定利用、権限維持、証跡保全、障害復旧を継続する。担当部署・受付時間・SLAは未確定のため、以下は運用設計案である。

## 2. 役割分担案

| 役割 | 主な責任 |
|---|---|
| 業務責任者（監査役） | 業務ルール、機密区分、アクセス承認、監査完了判断 |
| 監査役会 | 計画・重要指摘・重大例外・リスク受容の監督 |
| 総務部・監査事務局 | 日程、依頼、問い合わせ一次受付、手順・台帳維持 |
| システム管理者 | 設定、ID連携、監視、バックアップ、技術障害対応 |
| 情報セキュリティ責任者 | インシデント判断、ログ監査、脆弱性、委託先管理 |
| 被監査部門責任者 | 証憑提出、是正計画、完了証憑、部門内権限管理 |
| ベンダー | 契約範囲の製品障害・保守。監査内容へのアクセスは最小化 |

## 3. 定常運用

| 頻度 | 作業 | 証跡 |
|---|---|---|
| 日次 | 連携失敗、バックアップ、重大アラート、容量異常の確認 | 運用チェック記録 |
| 週次 | 未達通知、長期滞留、失敗ジョブ、サポート案件の確認 | 週次運用報告 |
| 月次 | 稼働率、障害、問い合わせ、容量、権限例外、ログ欠落の報告 | 月次報告 |
| 四半期 | 権限棚卸し、特権ID、外部共有、休眠アカウントの確認 | 承認済棚卸し票 |
| 年次 | 復旧・BCP訓練、保存・廃棄、委託先保証、手順見直し | 訓練・レビュー報告 |
| 監査終了時 | 案件権限閉鎖、作業ファイル整理、正本・索引確認 | クローズチェックリスト |

## 4. 問い合わせ・変更

問い合わせは「操作」「データ」「権限」「障害」「セキュリティ」に分類する。監査内容・判断は監査役へ、技術事項は管理者へ振り分ける。設定変更は[変更管理・リリース計画](変更管理・リリース計画.md)に従い、口頭依頼だけで本番変更しない。

## 5. 障害重要度案

| 重要度 | 例 | 初動目標案 | エスカレーション |
|---|---|---|---|
| S1 | 漏えい疑い、全停止、正本消失・改変 | 15分以内受付、直ちに封じ込め | 監査役、経営、情報セキュリティ、法務 |
| S2 | 主要業務停止、複数利用者の権限異常 | 30分以内受付 | 業務責任者、製品責任者 |
| S3 | 一部機能・連携障害、代替手段あり | 4営業時間以内受付 | 運用責任者 |
| S4 | 軽微な表示・操作質問 | 翌営業日以内受付 | ヘルプデスク |

数値は体制・契約確認後に承認する。

## 6. 障害対応フロー

```mermaid
flowchart LR
  A[検知・受付] --> B[重要度判定]
  B --> C[影響拡大防止]
  C --> D[証拠・ログ保全]
  D --> E[復旧・代替運用]
  E --> F[データ整合確認]
  F --> G[利用再開承認]
  G --> H[原因分析・再発防止]
```

- セキュリティ事案では、安易な再起動・ログ削除をせず証拠保全を優先する。
- 復旧後は件数、版、ハッシュ、参照、権限、ログを照合してから利用再開する。
- 重大障害は時系列、判断者、影響、対外通知、復旧、恒久対策を記録する。

## 7. 未確定事項

- 事故時の本人・当局・取引先への通知判断と期限。
