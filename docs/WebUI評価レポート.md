# WebUI評価レポート（Mirai Audit Workpaper MVP）

- **文書ID**: MAW-EVAL-001
- **版**: 1.0
- **作成日**: 2026-08-16
- **状態区分**: 評価結果（**検証中環境（mvp）** の実機確認に基づく。本番環境・実データでの評価ではない）
- **対象**: https://maw-mvp.mirai-dx-platform.com/（Cloudflare Workers + D1 の単一HTML・SPA方式）

## 1. 評価の目的と方法

- 目的: MVPのWebUIを業務利用者の視点で評価し、(a) 修正すべき事項、(b) 追加すべき機能・項目、(c) 左側メニュー化の実装案を示す。
- 方法:
  1. 実機ブラウザ操作（Chromium / Playwright）でログイン画面・ホーム・監査計画・監査案件・案件詳細・監査ログを確認（監査役／被監査部門（建設部）／監査役会の3ロール、PC・モバイル幅）。
  2. API応答の確認（ヘッダー・エラー形式・権限判定）。
  3. 実装ソース（`app/src/`）と要件定義書 MAW-RD-001（FR-01〜15）、`docs/実装・導入バックログ.md`（BL-01〜19）との突合。

## 2. 総評

基盤（認証・RBAC・状態遷移制御・監査ログ追記専用・CSRF対策・レート制限・D1スキーマ・48テストPASS）は堅牢で、設計思想は優れています。一方、UI/UXはプロトタイプ段階であり、**被監査部門が証憑提出フローに到達できない**等の致命的な操作断絶、編集操作の欠落、フィードバックのalert依存があります。業務受入（UAT）を進める前に、下記の優先度「致命的」の修正が必要です。

## 3. 良い点（維持すべき要素）

1. **権限設計**: ロール×操作のRBACと案件単位アクセス制御がコード化され、拒否時は監査ログに記録される（`permissions.ts`）。
2. **状態遷移の厳格化**: 計画・案件・依頼・調書・指摘それぞれに遷移マトリクスがあり、不正遷移は409で拒否（`security.ts`）。
3. **セキュリティ**: SameSite=Lax Cookie + Origin検証（CSRF）、IP/メール単位レート制限、CSP・X-Frame-Options等のヘッダー、パスワードはハッシュ保存。
4. **監査ログ**: 操作・拒否・IP・時刻を追記専用で記録（BL-03要件を満たす）。
5. **番号体系**: AUD/REQ/FND-YYYY-NNNN の年度一意連番がサーバ側で採番される。
6. **日本語エラー応答**: APIエラーが `{"error":{"code","message","correlation_id"}}` 形式で統一。
7. **基礎的なアクセシビリティ配慮**: `:focus-visible` 表示、`prefers-reduced-motion`、印刷用CSS、モバイル横スクロール対応。

## 4. 修正すべき事項（優先度順）

### 4.1 致命的（業務フローが成立しない／誤誘導する）

| No | 事項 | 状況（実機確認） | 対応方針 |
|---|---|---|---|
| F-01 | **被監査部門の「監査案件一覧」が常に空になる** | `renderEngagements()` が `Promise.all([engagements, plans])` で両方取得するが、被監査部門は `plan:view` 権限が無く plans が403 → 全体が失敗し「案件がありません」＋権限エラーのalertになる。API単体では案件は返っており表示可能 | 案件一覧はplans取得と分離し、権限のないロールではplansを取得しない。併せて403をalertではなく画面内メッセージ化 |
| F-02 | **被監査部門の証憑提出フローに到達できない** | ホームのタスク行はクリック不可、案件一覧はF-01で空のため、案件詳細（証憑依頼タブ→「証憑を提出」）へ導線が無い。実質「提出」操作がUI上不可能 | タスク行をクリック可能にし案件詳細へ遷移。F-01修正とセットで対応 |
| F-03 | **権限の無いロールに「監査計画へ」ボタンが表示される** | 被監査部門のホームに「監査計画へ」ボタンが出て、押すと「この操作の権限がありません」alert（監査ログにも `permission_denied:plan:view` が記録される） | ロール別にボタンを出し分け（`hasPermission(role,"plan:view")` で判定） |
| F-04 | **ブラウザの戻る・リロード・URL直接指定が機能しない** | SPAが `state.view` のみで管理しURLが一切変化しない。リロードでホームに戻る。深い画面を他者に共有できない | hashルーティング（`#/plans`、`#/engagements/:id` 等）を導入し、遷移をURLに同期させる |

### 4.2 高（業務品質・信頼性に直結）

| No | 事項 | 状況 | 対応方針 |
|---|---|---|---|
| F-05 | **証憑の「ハッシュ」が実ファイルのハッシュではない** | 提出フォームはファイル名を手入力し、クライアントで「ファイル名+補足+現在時刻」のSHA-256を生成するだけ。実ファイルのアップロード・保存・検証が無いため、証憑の真正性・完全性を担保できない | 実ファイルアップロード（R2等）＋サーバ側SHA-256検証＋サイズ・拡張子制限へ移行。移行までは「ハッシュ」表示をやめ「提出記録」として扱う |
| F-06 | **監査ログ画面が実務で使えない表示** | 操作者が `usr_xxx` の生ID、操作名が英語キー（`login`、`request_sent` 等）、対象IDが12桁トランケート。フィルタUIが無い（API側には `actor_id` / `object_type` / `action` フィルタ実装済み） | 操作者を氏名解決、操作名を日本語ラベル化、フィルタ・ページネーションUI追加、日時・詳細を整備 |
| F-07 | **是正計画の登録が「ユーザーID」の入力を要求** | `prompt("是正責任者（ユーザーID）:")` の3連続。人間は `usr_xxx` 形式のIDを知らないため入力不可能に近い | ユーザー選択ドロップダウン（部門絞り込み）＋フォーム化。alert/prompt/confirm を自作モーダルへ置換 |
| F-08 | **編集UIが皆無（バージョン管理が死んでいる）** | バックエンドには計画編集(PUT)、案件編集(PUT)、調書編集(PUT・版履歴)が実装済みだが、UIに編集ボタンが無い。調書の版履歴は作成時1版のみで増えない | 各画面に編集フォームと「新版として保存」を追加。調書は版の一覧・差分表示を用意 |
| F-09 | **パスワード運用が未整備** | 変更UIなし・複雑性要件なし（最小8文字のみ）・有効期限なし。mvp環境ではログイン画面にテスト用ID/パスワードがヒント表示される（環境判別で本番は非表示だが、テストアカウントの無効化手順が未定義） | パスワード変更・リセット・複雑性・期限を実装。テストアカウントは本番デプロイ時に必ず無効化する手順化 |

## 5. 追加すべき機能・項目

### 5.1 必須（業務成立のため。FR番号・バックログ対応）

1. **ダッシュボード（FR-11 / BL-11）**: 自分の承認待ち、依頼の期限超過、指摘の重要度別件数、是正の遅延状況を集計表示し、明細へドリルダウン。
2. **検索・一覧強化（FR-11）**: 年度・案件・部門・状態・重要度・期限の複合条件検索、ソート、ページネーション、CSV/Excel出力。
3. **通知・督促（FR-10 / BL-12）**: 依頼送付・期限前・期限超過・差戻し・レビュー依頼・承認待ちをアプリ内＋メールで通知。送信成否・既読を追跡。
4. **ファイルアップロード（FR-04）**: 実ファイルの保存（R2等）・サーバ側SHA-256検証・受領メタデータ（出所・提出者・受領日時・版）・マルウェア検査（将来）。
5. **報告書・帳票出力（FR-09 / BL-13）**: 監査報告書・指摘一覧・期限超過一覧のPDF/Excel生成、透かし、出力理由と出力ログ。
6. **ユーザー・組織管理（FR-12 / BL-16）**: 部門マスタ、ユーザーCRUD、役割変更履歴、退職・異動の即時反映、パスワードリセット。
7. **監査役会審議管理（FR-08 / BL-14）**: 審議事項・資料版・出席・論点・決定・留保・宿題を案件・調書に関連付けて記録。
8. **調書のリッチ編集（FR-05）**: Markdown編集・表・証拠（依頼/提出物）への参照リンク・テンプレート・版差分表示・署名日時。
9. **案件メンバー・利益相反（FR-12）**: メンバー追加/削除、レビュー担当の指名、利益相反フラグと除外、四半期棚卸しの出力。

### 5.2 重要（統制要件の充足）

10. **SSO・MFA（NFR-01 / BL-09）**: Entra ID／HENNGE ONE連携、特権操作の再認証、共有ID禁止。
11. **リーガルホールド・保存年限・廃棄（FR-14 / BL-04）**: 保全指定（保全中は削除・上書き不可）、保存年限管理、廃棄承認ワークフローと廃棄証跡。
12. **パスワードポリシー**: 変更・リセット・複雑性・有効期限・履歴。ログイン失敗時のアカウントロック。
13. **監査ログ運用**: フィルタ・エクスポート・操作者名解決・期間指定（F-06と一体）。
14. **依頼への質疑スレッド**: 被監査部門と監査側のやり取り（質問・回答・差戻し理由）をスレッドで記録。
15. **期限延長・再通知・一括送付（FR-03）**: 依頼の期限変更（理由・承認記録付き）、再通知、複数依頼の一括送付。
16. **監査計画の改訂履歴（FR-01）**: 承認済み計画の次年度版・改訂版のスナップショット管理（現在は版番号のみで内容履歴が残らない）。
17. **監査手続・サンプリングの記録（FR-02）**: 実施手続、サンプル抽出の根拠（母集団・抽出方法・件数）を案件に記録。

### 5.3 将来構想

18. **AI支援（FR-15 / BL-17）**: 許可された情報区分のみの要約・論点候補・類似調書検索。根拠リンクと「AI生成」表示を必須とし、人の確認を経ない確定操作は不可。
19. **正本庫連携（IF-02 / BL-15）**: DirectCloud等との版・ハッシュ・URI・保全連携。
20. **会計監査・内部監査との連携（IF-04 / BL-18）**: 許可済み計画・論点の共有。
21. **退出・移行支援（NFR-17 / BL-19）**: メタデータ・履歴・ファイルの可読形式エクスポート。

### 5.4 共通・横断

- **ロール別ホーム**: タスク中心のホーム（承認待ち・期限間近・差戻し・レビュー待ち）に再構成。
- **操作ログとの連動**: 閲覧ログ（誰が何を開いたか）の記録（FR-13の「閲覧」要件に対応）。
- **アクセシビリティ**: スキップリンク、nav/landmarkのARIA、キーボード操作、コントラスト検証。
- **用語の統一**: 画面ラベルを `docs/用語集.md` に合わせる（例: 「指摘」と「発見事項」の使い分け、「差戻し」表記の統一）。

## 6. 左側メニュー化の提案（ご要望対応）

### 6.1 情報設計（推奨レイアウト）

```
┌─────────────────────────────────────────────────────┐
│ トップバー: 🧭 監査業務・証跡管理 │ 検索 │ ユーザー名(ロール) │ ログアウト │
├──────────┬──────────────────────────────────────────┤
│ サイドバー │  メイン領域（パンくず＋コンテンツ）           │
│ (240px)  │  ホーム > 監査案件 > AUD-2026-0001 > 指摘・是正 │
│          │                                            │
│ ▸ ホーム  │                                            │
│ ▸ 監査計画 │                                            │
│ ▸ 監査案件 │                                            │
│ ▸ 証憑依頼 │                                            │
│ ▸ 監査調書 │                                            │
│ ▸ 指摘・是正│                                            │
│ ▸ 監査役会 │                                            │
│ ▸ 報告書・出力│                                          │
│ ▸ 監査ログ │                                            │
│ ▸ 設定     │                                            │
└──────────┴──────────────────────────────────────────┘
```

- **トップバー**: システム名・グローバル検索・ログインユーザー情報に限定（現在のヘッダーからメニューを分離）。
- **サイドバー**: 固定表示（幅240px）、折りたたみ可能（アイコン表示に縮退、1280px以下で自動折りたたみ）。
- **メニュー構成**: 業務フロー順（計画→案件→依頼→調書→指摘→報告）にグルーピングし、各項目に件数バッジ（例:「承認待ち 3」）。
- **ロール別出し分け**: 現行の `nav` 生成ロジックを流用し、権限の無い項目は非表示（F-03の再発防止）。
- **案件内ナビ**: 案件詳細の3タブ（証憑依頼／監査調書／指摘・是正）は案件内サブタブとして維持するか、サイドバーにサブメニュー展開（開いている案件に応じて）。
- **パンくず**: 現在地を明示し、上位一覧へワンクリックで戻れるようにする。
- **モバイル**: ハンバーガーでオーバーレイ展開、本文はフル幅。アクティブ項目と開閉状態を保持。

### 6.2 実装のポイント（`app/web/index.html` 変更案）

1. **CSS**: `body` をグリッド化（`.sidebar` + `.main`）。ヘッダーはトップバー専用に縮小。
2. **HTML生成**: `render()` 内の `<nav>` 生成を `sidebarHTML(me)` に置換。`state.view` からアクティブ項目を決定。
3. **ルーティング**: hashルーティング（`#/home`、`#/plans`、`#/engagements/:id`）を導入し、`hashchange` で `state.view` を更新。これにより戻るボタン・リロード・URL共有が機能する（F-04の解消）。
4. **注意点**:
   - 既存テスト（48件）はAPI層のテストなので、UI変更の影響は受けない。
   - `embedded-assets.ts` へのHTML埋め込みは `scripts/build-embedded.mjs` の再実行が必要（デプロイ手順に組み込まれていることを確認）。
   - サイドバー化はアクセス制御とは無関係に、表示制御のみで行う（権限判定は引き続きサーバ側）。
   - 折りたたみ状態は `localStorage` に保存してユーザー体験を維持。

## 8. 付録: 実機確認メモ（要点）

- ログイン: 監査役／被監査部門（建設部）／監査役会のシードアカウントで成功。ログイン画面にテスト用認証情報のヒントが表示される（mvp環境のみの仕様）。
- 監査役: ホーム（タスク2件）→ 監査計画（2026年度計画 approved）→ 監査案件（AUD-2026-0001）→ 案件詳細（依頼・調書・指摘タブ、各「新規」ボタン動作）→ 監査ログ（操作者ID・英語キー表示を確認）。
- 被監査部門: ホームに「監査計画へ」ボタンが出るが権限エラーalert。「監査案件一覧」は空（F-01）。API上は案件が返っており表示可能なことを確認。
- コンソール: CSPによる `static.cloudflareinsights.com/beacon.min.js` ブロック、未ログイン時の `/api/me` 401（F-19、F-22）。
- HTTPヘッダー: CSP・X-Frame-Options・nosniff・Referrer-Policy等は設定済み。HSTS未確認（F-21）。
- 関連文書: `docs/実装・導入バックログ.md`（BL-04, BL-09〜19 未着手）、要件定義書 FR-01〜15。
